# EBIE Implementation — Open Questions for the AI Engineering Team

**Re:** `INFUSION-ADVANCED-EARLY-BREAKOUT-SCANNER-BLUEPRINT.md` (64 sections, Early Breakout Intelligence Engine)
**Prepared:** 2026-08-19
**Purpose:** Before writing any code against this blueprint, these are the decisions and unknowns that materially change scope, cost, or architecture. Each question is grounded against the *current, real* Infusion codebase (checked directly, not assumed) — not a generic requirements checklist.

This is not a "we can't do it" list. Every item below is answerable and most have a reasonable default; they're flagged because picking wrong burns real time (a new microservice split, a Postgres schema that has to be migrated twice, a data subscription tier that turns out insufficient three phases in).

---

## 1. Scope: all of it, or a subset first?

The blueprint specifies 15 phases (EB-0 through EB-14), each a real multi-week module: data integrity, state machine, accumulation/compression, relative strength, futures positioning, dynamic options, microstructure, sentiment/NLP, unified verdict, trap model, ML meta-classifier, portfolio risk, dashboard redesign, shadow validation, champion promotion.

- **Q1.1** — Is the full 15-phase build authorized, or should we scope an MVP subset first (e.g., EB-0 through EB-3, no microstructure/sentiment/ML-ladder yet) and get a checkpoint before continuing? Given every phase in Infusion's history to date has shipped as an independently verified, committed increment, EBIE would naturally follow the same discipline — but 15 phases at that granularity is a materially longer roadmap than anything built so far in one continuous run.
- **Q1.2** — Section 43 explicitly says *"do not build a huge deep-learning model before labels are proven"* and Section 14 mandates a model ladder (logistic → boosted trees → sequence models, "only if proven necessary"). Is there team appetite to genuinely stop at level 2 (boosted trees) if it doesn't beat level 1, or is there an expectation that this eventually reaches a transformer/sequence model regardless?
- **Q1.3** — Who is the primary implementer — is this now a multi-engineer build (hence "checking with the AI engineer team"), and if so, does the team want the phases built in strict sequence by one owner, or parallelized across engineers by module (e.g., one on microstructure, one on sentiment, one on the state machine)? This changes how tightly the phases need to be decoupled at the interface level from day one.

## 2. Real capability gaps found in the current codebase (checked directly, not assumed)

These aren't open design questions so much as **facts the team needs before estimating effort** — several blueprint sections assume infrastructure that doesn't exist yet at all, not infrastructure that needs extending.

- **Q2.1 — Market depth is currently top-of-book only.** `services/ingestion/src/ingestion/adapters/upstox_codec.py` parses exactly one depth level (`first_depth`: best bid/ask price + quantity). The blueprint's entire Section 4.6 (Order-Book/Microstructure Pressure Engine) requires **multi-level depth** (`sum(weight_i * bid_qty_i)` across "top N levels", bid/ask replenishment, sweep detection). This is not a feature-engine change — it's a new ingestion subscription mode (Upstox's `full_d5`/`full_d30` feed modes, per the blueprint's own Section 44/262 caveat about 30-level depth being more restricted). **What Upstox plan/entitlement does the account currently hold, and does it include multi-level depth? If not, is upgrading it authorized, and what's the added cost?**
- **Q2.2 — There is no news/sentiment pipeline at all today.** No FinBERT, no NLP library, no Upstox News API integration exists anywhere in the codebase (checked: zero matches for `news`, `sentiment`, `finbert`, `nlp` across all services). Section 4.10/EB-7 is a from-scratch build, not an extension. **Does the team want to self-host FinBERT (GPU/CPU inference cost, model hosting), or call a hosted NLP/sentiment API? Is there budget for either?**
- **Q2.3 — No ML dependency beyond plain Python exists.** `services/api/src/api/ml_classifier.py` is a hand-written L2-regularized logistic regression with no numpy/sklearn — a deliberate choice made when the classifier was first built (avoiding a new fragile dependency for a single model). Section 14's model ladder (LightGBM/XGBoost/CatBoost) means adding a real ML dependency to the `api` service's Docker image for the first time. **Is a boosted-tree library an acceptable new dependency, and does it need a separate training/serving process, or is api-service in-process training (like today's logistic regression) still acceptable at that model complexity?**
- **Q2.4 — No portfolio-level risk tracking exists.** Confirmed zero matches for `portfolio_fit`, `portfolio_risk`, `sector_concentration`, `directional_delta` anywhere in the codebase. This was explicitly flagged as "never scoped" in Infusion's own project plan before this blueprint arrived. Section 26 calls this **mandatory before capital scaling** — but Infusion is paper-trading only today with no live capital at risk. **Given there's no live capital exposure yet, is EB-11 (Portfolio Risk) still a near-term priority, or can it move later in the sequence than the blueprint's own EB-8→EB-11 ordering suggests?**
- **Q2.5 — No futures OI velocity/basis tracking exists.** Confirmed zero matches for OI-velocity/basis-change features anywhere. Section 4.7/EB-4 is fully new — Infusion's existing options work (PCR, Max Pain, OI-based S/R, IV Rank) covers the *options* side but never touched *futures* positioning specifically. **Does current market data ingestion even pull stock-futures LTP/OI, or does that need a new instrument subscription per symbol (doubling relevant subscriptions from options-only to options+futures)?**
- **Q2.6 — No probability calibration exists.** The current ML classifier reports AUC/lift, not a calibrated probability. Section 7 requires Platt scaling or isotonic regression with tracked Brier score / reliability diagrams before any number is shown to the user as "X% probability." **Is a real, standalone calibration step scoped as its own deliverable (with its own verification bar — a reliability diagram, not just an AUC number), or does "probability" in early EBIE releases stay explicitly labeled as an uncalibrated score until enough outcomes accumulate to calibrate honestly?**

## 3. Real overlap with what's already built — replace, extend, or run in parallel?

This is the highest-risk category: building EBIE's versions of these without an explicit decision risks **three competing systems answering the same question differently**, which is worse than either one alone.

- **Q3.1 — Three "early state" trackers already exist; EBIE proposes a fourth.**
  - `PreBreakoutTracker` (scanner service) — already tracks COMPRESSING/ACCUMULATING/COILED states per symbol, and is explicitly protected from being wiped by non-chaseable publishes (Phase W's fix).
  - `stock_breakout_tier` (api/ticks.py) — already outputs EARLY_WATCH → BREAKOUT_NOW → RETEST_ENTRY → OPTION_READY / NO_CHASE per stock, with a 0–100 `stock_breakout_score`.
  - `radar_alerts` (Postgres table, R9) — already tracks a dashboard-only early-alert lifecycle: fires on first EARLY_WATCH+ crossing, resolves to GRADUATED / FADED / EXPIRED.

  Section 5's proposed state machine (IDLE → DEVELOPING → PRE_BREAKOUT → READY → ARMED → TRIGGERED → CONFIRMED → CONTINUATION/FAILED) covers essentially the same conceptual ground with different state names and more granularity. **Does EBIE's state machine (EB-1) replace all three of the above outright, get built as a genuine fourth layer that supersedes them once proven (with the old three deprecated after a shadow period), or do the existing three stay as-is with EBIE's state machine sitting logically "above" them as a different, more advanced product tier?**
- **Q3.2 — Episode freezing is already built, twice.** Section 28's "episode freezing" spec (freeze `episode_id`/trigger/invalidation/targets at READY or ARMED, keep visible even as live metrics update) is *exactly* what Phase W already built for `options_first_hybrid.py` and `vol_vwap_breakout.py` — the watch-episode freeze that stops the GRASIM-style repeat-alert-with-drifting-ladder bug. **Is the ask to extend this existing, already-verified mechanism to cover the new EBIE state machine's states, or to design a separate one? (Extending is very likely the right call — this is flagged so the team doesn't accidentally rebuild something that's already live and proven.)**
- **Q3.3 — VCP already covers a real slice of Section 4.3's "compression."** The existing VCP score (Minervini Stage-2: trend template, contraction quality, volume dry-up, pivot proximity, RS) is a genuine, verified implementation of volatility-contraction detection — but it's a **daily-bar, swing-timeframe** feature, not the intraday CLV/RVOL_TOD/AVWAP-hold accumulation model Section 4.3 wants for the intraday model. **Does VCP get reused as-is for the short-swing model's compression evidence family (Section 9), with EB-2's new intraday accumulation features being genuinely separate and additive, or does the team want compression logic unified into one component that serves both horizons?**
- **Q3.4 — PCR/Max Pain/OI walls exist but are the "static" version the blueprint says to remove.** Section 11.5/11.6/11.7 explicitly call out removing static-threshold PCR, static Max Pain direction, and "highest call OI = resistance" as standalone signals — which is close to how Infusion's current `options_analytics.py` presents them today (real PCR/Max Pain/OI-S-R numbers, but not yet velocity/migration/z-score framed). **Is EB-5 (Dynamic Option Chain) a rework of the existing `options_analytics.py` module in place, or a new parallel module, with the old static reads deprecated from the verdict once the dynamic version is verified?**
- **Q3.5 — Signal Alignment Gate already does a version of "evidence family, not raw feature count."** Phase 13.9 already built an N-of-M independent-factor-agreement gate before a signal fires — conceptually close to Section 20's feature-cluster/anti-double-counting idea, though scoped narrower (a pre-alert gate, not the full bull/bear scoring architecture of Section 6). **Should EB-8's Unified Verdict Engine subsume/replace the existing signal-alignment gate, or run alongside it as a second, independent check?**
- **Q3.6 — Delivery %, VWAP SD bands are built; multi-anchor AVWAP is not.** Section 4.4 wants many AVWAP anchors (session open, prior day H/L/C, week/month open, swing points, gap days, event candles) — today Infusion has session VWAP + SD bands only, no anchoring beyond the current session. **Is multi-anchor AVWAP scoped as part of EB-2, or does it wait — it's explicitly useful for both the intraday and swing models per Section 4.4/4.5's example pattern, so sequencing it matters.**

## 4. Architecture

- **Q4.1 — New shell exclusivity (Section 11.10).** The blueprint says new intelligence features should target the New shell only going forward, with Classic maintained "temporarily" for stability, to avoid double-building every visualization. Infusion's dashboard work to date has deliberately kept **both** shells at feature parity through every phase so far (per the project's own "keep both until checked against real market conditions" policy). **Is this the point where that policy changes — New shell becomes the sole target for all EBIE-era UI, and Classic is frozen (bug-fixes only, no new features) starting now? If so, is there a target date/criterion for retiring Classic outright, or does it stay indefinitely as a fallback?**
- **Q4.2 — Sentiment engine as a separate microservice (Section 29).** The blueprint proposes `sentiment-engine/` as the one new standalone service, justified by NLP's different lifecycle (model loading, inference latency, possibly GPU) versus the rest of the stack. **Does the team agree with this specific split, or would it rather live as a module inside `api` or `scanner` initially (matching the "start as modules, split only when operational evidence requires it" principle the blueprint itself states in Section 29's own justification) — i.e., should EB-7 build it in-process first and only extract it once real latency/load numbers justify a service boundary?**
- **Q4.3 — Redis/Postgres capacity plan.** Section 31 proposes 12 new tables (`market_feature_snapshots`, `derivative_snapshots`, `option_strike_snapshots`, `news_events`, `sentiment_scores`, `scanner_episode_states`, `verdict_snapshots`, `trap_predictions`, `model_predictions`, `model_calibrations`, `feature_versions`, `experiment_runs`, `portfolio_risk_snapshots`), most storing a **full feature snapshot per candidate per evaluation** for reproducibility (Section 15/48). At 208 symbols evaluated on some cadence with option-chain + futures + microstructure + sentiment all snapshotted together, this could be a large multiple of current Postgres write volume. **Is there a retention/archival policy expected from day one (e.g., raw snapshots kept 30–90 days, only outcomes kept indefinitely), or should full history be retained permanently? This affects schema design (partitioning) from the first migration, not something to bolt on later.**
- **Q4.4 — Tiered scanning (Section 4.2) is a real architecture change to the hot path.** Today, `list_ticks()`/`_scanner_intel()` compute the same depth of analysis for all ~208 symbols on every poll — there is no "Tier 1 cheap scan → Tier 2 candidate promotion → Tier 3 full depth" dynamic subscription model anywhere in ingestion or the scanner. Building this changes how `ingestion` manages its Upstox WebSocket subscriptions dynamically at runtime (subscribe/unsubscribe per-symbol depth mode as candidates get promoted/demoted) — a meaningfully different pattern from the current fixed, symbol-list-at-boot subscription model. **Is dynamic subscription management (EB-0/EB-6 territory) in scope for the first EBIE milestone, or does the team accept scanning all 208 at Tier-1 depth uniformly for now, deferring Tier 2/3 promotion until microstructure (EB-6) is actually being built?**

## 5. Modeling & evaluation

- **Q5.1 — Breakout label thresholds (Section 13).** The blueprint gives example numbers (intraday: 45 min horizon, +0.75 ATR success before −0.50 ATR invalidation; swing: 3 sessions, +1.50 ATR before −0.75 ATR) explicitly as "research starting points, not permanent thresholds," to be calibrated by symbol liquidity/regime/volatility. **Should these exact starting numbers be used for the first labeling pass, or does the team want a calibration study run first against Infusion's own 12,000+ archived outcomes to pick better starting points specific to this universe?**
- **Q5.2 — Shadow-mode promotion criteria (Section 38/Q59).** The blueprint requires "sufficient real unseen outcomes" before a new model/feature can affect live verdicts, but doesn't fix a number. **What's the minimum sample size and shadow-mode duration the team wants before promoting EBIE's verdict engine to replace/augment the current live alert flow? Given the F&O session's real daily signal volume (roughly a dozen or so fired signals per day historically), a meaningful shadow sample could take weeks — is that timeline acceptable, or does the team want a synthetic/backtested pre-validation gate to shorten the wait before live shadow mode even starts?**
- **Q5.3 — Champion/challenger cadence (Section 39).** Once a challenger model exists, how often should it be re-evaluated for promotion — every trading day, weekly, or only on-demand when someone notices decay? This affects whether EB-14 needs its own scheduler loop or is a manual/analyst-triggered process initially.

## 6. Risk & product policy

- **Q6.1 — Hard gates list (Section 42) needs a final, explicit sign-off.** The blueprint's example list (F&O ban, market closed, stale quotes, insufficient option liquidity, extreme spread, missing trigger/invalidation, data-quality failure, portfolio risk limit exceeded) blocks a trade outright rather than just penalizing score. Given Infusion is paper-trading only, is there real appetite for `portfolio risk limit exceeded` to hard-block a *paper* verdict, or should portfolio-level flags stay informational (shown, not blocking) until live capital is ever at risk?
- **Q6.2 — Data Quality Score threshold (Section 4.1).** The blueprint says `data_quality_score < threshold → DATA UNRELIABLE — NO TRADE` but doesn't set the threshold. Does the team want this threshold set conservatively from day one (erring toward more "NO TRADE" verdicts while the score's own reliability is unproven), or tuned only after watching real data-quality-score distributions for a few weeks?
- **Q6.3 — Verdict grade thresholds (Section 24)** are explicitly marked "do not hard-code final thresholds until calibration is complete," with example starting bands (<55 NO EDGE, 55–64 DEVELOPING, 65–74 PRE-BREAKOUT WATCH, 75–84 READY, 85+ ARMED). Same question as Q5.1 — start with these exact numbers, or calibrate against archived history first?

## 7. External dependencies to verify before committing to the plan

The blueprint itself (Section 44/63) already flags that "provider schemas, entitlements, subscription limits and exchange rules can change" and instructs the implementation team to verify current documentation at integration time. Concretely, before EB-0 starts:

- **Q7.1** — Confirm current Upstox account tier actually includes: multi-level market depth feed mode, option Greeks feed, News API access, and whatever rate limits apply once per-symbol subscriptions roughly double (options + futures + deeper depth vs. today's LTP/quote/option-chain-on-demand pattern).
- **Q7.2** — Confirm whether the Upstox News API has a cost tier, request-volume limit, or latency profile that affects EB-7's design (polling cadence, caching strategy).
- **Q7.3** — Confirm NSE's official delivery/derivatives reports (used for EOD delivery % today, and referenced again for validation/EOD research in Section 45) haven't changed format or access terms since Phase 13.5 last touched that scraper — that integration already once needed a real bug fix for a 403/idempotency issue and is worth a quick health check before building more on top of it.

## Summary for a fast answer

If the team wants to unblock EB-0 immediately without resolving every question above, the minimum decisions needed right now are:

1. **Scope** (Q1.1): full 15-phase build, or MVP subset first?
2. **Depth data** (Q2.1): is multi-level depth entitlement available/approved, given EB-6 (microstructure) depends on it entirely?
3. **State machine ownership** (Q3.1): does EBIE's state machine replace the existing three overlapping trackers, or sit alongside them?
4. **Shell target** (Q4.1): New shell only from here forward, or keep dual-shell parity?

Everything else can reasonably be decided phase-by-phase as EB-0 through EB-3 actually get built, matching how every prior phase of this project has been scoped — implemented, verified live, then the next phase's open questions get resolved with real data in hand rather than guessed up front.
